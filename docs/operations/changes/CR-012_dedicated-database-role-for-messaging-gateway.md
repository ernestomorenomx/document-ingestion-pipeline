# CR-012: Dedicated database role for the messaging gateway

- Date: 2026-11-03
- Findings addressed: BV-F-025 (partially: the gateway only; the workflow engine and the pipeline still use the superuser role). BV-F-027 was registered from evidence found while preparing this change.
- Approved by: owner, in the working session
- Backup taken (required): A custom-format dump of the gateway database and an archive of its data folder, both kept in the owner's home folder with owner-only permissions. The dump was restored into a temporary database before any change and the total row count matched (60 rows in the public schema). The data folder archive was 159 bytes, so that folder holds almost nothing. The previous container stayed on disk.
- Change: Created a login role without superuser, create-database, create-role, replication or row-security-bypass rights, with a random password stored in the password manager. Transferred ownership of every table, sequence, type and routine in the public schema, and of the database itself, to that role in one transaction. Revoked the public CONNECT privilege on the gateway database and on the main database. Recreated the gateway container from the same image ID with the same network, port, restart policy and volumes (taken from the old container); the only changed variable is the database connection string, which now uses the new role. The old container was renamed and stopped with its restart policy disabled.
- Rollback: Remove the new container, rename the old one back, restore its restart policy and start it. The old container still holds the previous connection string and the superuser role keeps access to every object, so no database change has to be undone. Not used.
- Verification (required): Observed in script output: the restored row count equalled the live count (60); no objects remained owned by the superuser role after the transfer; the row count after the transfer was unchanged; a real network login with the new role from a throwaway container returned the new role name with superuser false; the same role was refused on the main database with a missing CONNECT privilege. The cutover script reported HTTP 200 on the gateway port, 5 sessions of the new role in the database and 17 seconds of downtime, and its own comparison of ports, mounts and variable names against the old container passed. A later read-only check showed the new container up, the database owners as intended and 10 successful workflow executions in the previous 15 minutes (that window does not cover the cutover itself). One check string in the first script expected "f" where PostgreSQL printed "false" and stopped it after step 6; the remaining checks were run by hand with the results above.
- Residual risk: The old container keeps the superuser connection string in its variables until it is removed (planned about a week after this change, with an addendum). The gateway still runs on a floating image tag (BV-F-023) and its port is still published on all interfaces (BV-F-016). The dump in the owner's home folder contains message data and has to move to encrypted storage or be deleted. The gateway database is still not in the scheduled backup (BV-F-027).
