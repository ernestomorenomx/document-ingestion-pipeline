# CR-014: Database port restricted to the local host

- Date: 2026-11-03
- Findings addressed: BV-F-016 (partially: the database port; the workflow engine, the messaging gateway and the file-sync web service are still published).
- Approved by: owner, in the working session
- Backup taken (required): The scheduled backup service was started by the script immediately before the change and dumped both databases (the new job from CR-013). The old container stayed on disk, stopped, with its restart policy disabled, and its data folder is inherited by the new one, so no data was copied or moved.
- Change: Before the change, a connection test from another machine over the private network reached the database port (observed). A 6-minute sample of active sessions, 36 samples, showed only two internal sources: the messaging gateway and the workflow engine, both over the internal container network, and no session from outside; no common database client was found on the owner's laptop (observed). The container was on two networks (the default one and the project one). A script recreated it from the same image ID with the same variables, volumes, restart policy and both networks, publishing the port only on the loopback address, after a clean shutdown of the database. The script then compared row counts, checked the published port, and restarted the messaging gateway so it reconnects.
- Rollback: Remove the new container, rename the old one back, restore its restart policy and start it; the script does this automatically if any check fails. Not used.
- Verification (required): Observed in command output: the script reported the port bound to loopback only; row counts equal before and after (24 in the main database, 60 in the gateway database); internal addresses unchanged on both networks; 16 seconds of downtime. From the owner's laptop the same connection test that succeeded before now failed. A later check showed the database and gateway containers up for 3 minutes, 4 sessions of the gateway role, and 21 successful workflow executions in the previous 30 minutes with no failed ones.
- Residual risk: Remote access to the database now needs an SSH tunnel over the private network. The old container keeps its variables, including the superuser password, until it is removed (planned with the other old containers, with an addendum). The script is a one-off and is not stored in the repository, so the container still has no declarative definition (see the compose gap noted in the README). Only 36 samples over 6 minutes backed the claim that no outside client exists, so an occasional client could have been missed; none was reported. The script removes its temporary file of variables, and that removal was not separately checked. A first version of the script stopped before any change on two unexpected container settings; the tests of those guards are why the container's two-network setup is now recorded here.
